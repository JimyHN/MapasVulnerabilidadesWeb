# 👤 2. Pérdida de autenticación

Se basa en que, **debido a errores al implementar incorrectamente procesos como la autenticación y la gestión de sesiones,** permite al atacante **utilizar esos errores para hacerse pasar por otro usuario.**

<div style="display: flex; justify-content: space-between; align-items: center;">
  <img src="riesgosauten.png" alt="Imagen 1" style="width: 100%; border-radius: 8px;">
</div>

Uno de los problemas por los que se produce esto es porque el **protocolo HTTP es un protocol sin estados,** es decir, que cada petición es una petición nueva, ejemplo:

*\- ¿Podrías servirme un café?
\+ Si claro, tome
\- ¿Y azúcar?
\+ ¿Azúcar para que?*

O que es necesario recordar ciertas variables asignadas al usuario final como **inicio de sesión/contraseña,** que las **credenciales principales deben acompañarse en cada solicitud** o que **se debería de emplear SSL** cada vez que sea requerida una credencial.

Las **sesiones** sirven para que el servidor reconozca a cada usuario individualmente, ya que el protocolo web por sí solo no tiene "memoria" para saber quién es quién. Para esto se usa un identificador llamado **SESSION_ID**, el cual viaja por la red y permite mantener tu estado (como tu carrito o perfil) activo sin pedirte la clave en cada clic. Sin embargo, si un atacante roba ese ID, puede entrar en tu cuenta y falsear tu identidad tan fácilmente como si tuviera tu propia contraseña.

Por lo que, los escenarios donde se produce este **fallo de autenticación son:**

- **Aplicación de viajes que no destruye sesiones**
	- Se lo mandamos a nuestros familiares para que vean lo que nos ha costado y dónde nos vamos a ir de viaje. Un usuario malicioso lo intercepta y lo modifica
	- Como la sesión no ha sido destruida, conseguirá su billete a cargo de la otra persona y con otro destino completamente diferente.

- **Sesiones mal almacenadas en local**
	- Cibercafé donde navegamos
	- Hemos acabado y cerramos la pestaña
	- Un usuario malicioso accede al mismo equipo y recupera la sesión con el historial que proporciona el *browser*
- **Hosing compartido**
	- Al compartir un hosting, todas las sesiones son almacenadas en el mismo directorio
- **Mala gestión de la autenticación**

# 🦴 3. Exposición a datos sensibles (XXE)

Muchas aplicaciones web y API tienen acceso a información sensible de usuarios, como **datos bancarios, salud o identificaciones personales,** los atacantes pueden robar o modificar dicha información para llevar a cabo **fraudes, robos bancarios o suplantación de identidad.**

Es por ello que los datos sensibles requieren de **métodos de protección adicionales, como el cifrado en cada almacenamiento y tránsito.**

Al no cifrar correctamente la información, como **almacenar claves de forma insegura, usar algoritmos débiles o no rotar las claves** se produce esto, también se puede producir al emplear **hashes inseguros y sin salt.**

Un **hash** es el resultado de aplicar una función matemática que transforma una contraseña en una cadena de caracteres única y de longitud fija. Su propósito fundamental es proteger la información, ya que es una operación de un solo sentido: se puede obtener el hash a partir de la contraseña, pero no se puede (teóricamente) reconstruir la contraseña original a partir del hash.

Si son inseguros, se pueden vulnerar por fuerza bruta, y sin salt, la **salt** es la que hace que si dos usuarios tienen la misma contraseña, gracias a esta, que es un dato aleatorio que se añade a las contraseñas, logramos que sean diferentes entre si

**Es importantísimo usar siempre SSL**

El **SSL** (Secure Sockets Layer) es una tecnología estándar de seguridad que garantiza que los datos transmitidos entre un navegador y un servidor viajen de forma cifrada y privada.

Aquí tienes los puntos clave según la información de tus imágenes:

- **Protección de datos**: Se utiliza para asegurar que las credenciales de acceso y el **ID_SESSION** estén protegidos en todo momento durante la transmisión.
    
- **Seguridad en cookies**: Es necesario para que las cookies de usuario puedan transmitirse mediante el atributo **SECURE**, lo que impide que sean enviadas a través de conexiones no cifradas.
    
- **Verificación**: Una de las tareas críticas al revisar una aplicación es comprobar la validez del **certificado SSL** para asegurar que la identidad del sitio sea legítima.

# 🛸 4. Entidades externas XML

Muchos procesadores XML antiguos o mal configurados evalúan referencias a entidades externas y en documentos XML. Las entidades externas pueden utilizarse para revelar archivos internos mediante la URI o en servidores no actualizados, escanear puertos de la LAN, ejecutar código de forma remota y realizar ataques de denegación de servicio (DNS)

Este tipo de fallos se pueden llegar a producir en **las aplicaciones que reciben como entrada un documento XML** y para procesarlo hacen uso de alguna librería de procesado como LibXML, Xerces, MiniDOM, etc. Es decir, se produce en aplicaciones que hacen uso de _parsers_ XML.

- **En qué consiste:** Ocurre cuando una aplicación acepta archivos XML y utiliza un procesador (librería) que está mal configurado. El atacante incluye en el XML una "entidad externa" (una especie de variable) que apunta a un recurso fuera del documento.
    
- **Cómo se explota:** Al procesar el archivo, la librería intenta resolver esa entidad. Si apunta a un archivo del sistema (como `/etc/passwd`), el servidor lo lee y se lo muestra al atacante.

- Otro uso es para el **escaneo de la red local (LAN),** o para realizar una **denegación de Servicio (DoS)** bloqueando el servidor mediante archivos XML.

Para evitar este tipo de vulnerabilidad, donde a través de este, el atacante puede hacerse con todo, es recomendable **usar otros formatos como JSON** que es más seguro

# 🏃‍♂️ 5. Perdida de control de acceso

Las restricciones sobre lo que los usuarios autenticados pueden hacer no se aplican correctamente, con lo que los atacantes pueden explotar estos defectos para acceder, de forma no autorizada, a funcionalidades, datos y cuentas de otros usuarios, ver archivos sensibles, modificar datos, cambiar derechos de acceso y permisos...

**El atacante hace uso de una autenticación válida para acceder a objetos para los cuales no tendría autorización o permiso.** En estos casos, las aplicaciones suelen emplear el nombre o la clave de un objeto sin validar que realmente cuente con la autorización necesaria.

<div style="display: flex; justify-content: space-between; align-items: center;">
  <img src="riesgoscontrol.png" alt="Imagen 1" style="width: 100%; border-radius: 8px;">
</div>

**Las restricciones de control de acceso implican que los usuarios no pueden actuar fuera de los permisos previstos.** Si esto no se gestiona adecuadamente, puede ocasionar la **divulgación, modificación o destrucción no autorizadas de los datos o realizar una función de negocio fuera de los límites del usuario.**

Se puede evitar **implementando mecanismos de control de acceso, uso de tokens JWT deben de ser invalidados después de la finalización de la sesión, o el listado de directorios del servidor web que deben deshabilitarse.**

# 👷 6. Configuración de seguridad incorrecta

Al establecer la configuración de forma manual, ad hoc o por omisión (o directamente por falta de configuración) se produce este error en la seguridad.

Significa que el sistema es vulnerable porque se dejó con los valores de fábrica (omisión), se ajustó manualmente sin seguir un estándar o se improvisó una solución rápida e incompleta (ad hoc) para un problema puntual. Esto genera fallos de seguridad al no existir una configuración planificada, documentada y protegida de manera profesional.

**Ad hoc** se refiere a soluciones improvisadas o configuradas específicamente para un momento puntual sin seguir un estándar de seguridad. Esto genera vulnerabilidades al carecer de una planificación global, dejando el sistema expuesto por errores manuales o parches temporales.

# 🎭 7. Secuencias de comandos en sitios cruzados (XSS)

Esta sección detalla cómo la **Exposición de datos sensibles** y el **XSS** comprometen la seguridad al no proteger información crítica como datos financieros o PII. Mientras la primera se debe a fallos en el cifrado y gestión de claves, el XSS permite a atacantes secuestrar sesiones e inyectar scripts maliciosos (almacenados, reflejados o basados en DOM) directamente en el navegador de la víctima. Para evitarlo, es fundamental sanitizar entradas, usar protocolos **SSL/TLS** y configurar cookies con atributos de seguridad como **HttpOnly**.

Los scripts son un conjunto de instrucciones -generalmente, almacenadas en un archivo de texto- que deben ser interpretadas línea a línea en tiempo real para su ejecución. Se distinguen de los programas en que estos deben ser convertidos a un archivo binario ejecutable.

**Cómo se realiza el ataque:** El atacante detecta un campo que muestra datos sin filtrar y envía un script que el navegador de la víctima ejecuta como si fuera código legítimo del sitio. Esto permite al atacante robar el `SESSION_ID` de las cookies para suplantar la identidad del usuario y tomar el control total de su cuenta.

**XSS Directo o Persistente:** El código malicioso se guarda permanentemente en el servidor, como en bases de datos o comentarios, afectando automáticamente a cualquier usuario que visite esa sección de la web. Se basa en etiquetas como `<script>` que el navegador ejecuta al cargar la página infectada, siendo el tipo de ataque más peligroso por su alcance.

**XSS Indirecto o Reflejado:** El script no se almacena, sino que se "refleja" a través de un enlace malicioso o un formulario, requiriendo que la víctima haga clic en una URL manipulada. Es común en campañas de ingeniería social o phishing, inyectando el código mediante parámetros de búsqueda o archivos aparentemente inofensivos.

# 🪵 8. Deserialización insegura

La deserialización insegura es una vulnerabilidad que ocurre **cuando una aplicación procesa datos maliciosos provenientes de un usuario para reconstruir un objeto, permitiendo que un atacante manipule su estructura.** Esto puede llevar a ataques graves como la ejecución remota de código en el servidor, el robo de datos sensibles o la elevación de privilegios. Para prevenirlo, es fundamental validar los datos de entrada y utilizar mecanismos de seguridad como testigos (tokens) no predecibles en cada petición.

Imagina que una tienda online guarda tu carrito de compras en una "cookie" serializada que dice: `{"user": "invitado", "descuento": "0%"}`. Un atacante intercepta ese dato, lo modifica a `{"user": "admin", "descuento": "100%"}` y lo envía de vuelta; si la aplicación no valida el objeto al reconstruirlo (deserializarlo), le otorgará permisos de administrador y productos gratis.

# 🧨 9. Uso de componentes con vulnerabilidades conocidas

Esta vulnerabilidad ocurre cuando una aplicación utiliza **bibliotecas o frameworks desactualizados** que tienen fallos de seguridad ya identificados y públicos. Debido a que estos componentes suelen ejecutarse con los **mismos privilegios** que la aplicación, un atacante puede explotar sus defectos para **robar datos o tomar el control total del servidor**. Mantener el **software actualizado** es crítico, ya que los atacantes buscan activamente estas debilidades conocidas en archivos no protegidos para obtener acceso al sistema.

Imagina que tu aplicación web utiliza una versión antigua de una **biblioteca para procesar archivos PDF** que tiene un fallo de seguridad reportado públicamente. Un atacante, al saber que esa versión es vulnerable, envía un **archivo malicioso** que aprovecha ese error específico para **ejecutar comandos** directamente en tu servidor. Como ese componente se ejecuta con los **mismos permisos** que tu aplicación, el atacante logra acceso total al sistema sin necesidad de adivinar contraseñas.

# 🙈 10. Registro y monitoreo insuficientes

Esta vulnerabilidad ocurre cuando un sistema no **registra ni vigila adecuadamente las actividades sospechosas**, como intentos fallidos de inicio de sesión o errores críticos. Al no tener alertas configuradas, los atacantes pueden **permanecer ocultos durante meses**, extraer datos o destruir información sin dejar rastro. Esta falta de visibilidad impide una **respuesta rápida ante incidentes**, permitiendo que las brechas de seguridad sean detectadas tarde y generalmente por terceros en lugar de procesos internos.

Imagina que un atacante intenta **adivinar la contraseña** de un administrador realizando miles de intentos por hora. Si el sistema tiene un **registro insuficiente**, nadie se dará cuenta del ataque porque no se generan alertas por actividad inusual. Esto permite que el atacante finalmente entre, **robe información sensible** y borre sus huellas sin que la empresa lo detecte hasta meses después.

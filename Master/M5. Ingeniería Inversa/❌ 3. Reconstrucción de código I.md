
## Introducción a la Reconstrucción de Código

El proceso de compilación tradicional es aquel que transforma el código fuente, escrito por una persona en un lenguaje de alto nivel y fácil de entender, en **código objeto**. Este código objeto es lenguaje máquina, diseñado específicamente para una arquitectura de hardware concreta y que la computadora puede ejecutar directamente. Para llegar a este punto, el compilador pasa por varias fases: primero genera un código intermedio, luego aplica un optimizador para que el programa sea más eficiente y, finalmente, el generador de código produce las instrucciones binarias o de ensamblador finales. Comprender este camino es fundamental para entender el proceso inverso.

La **reconstrucción de código** es precisamente ese proceso inverso: intentar obtener el código fuente original a partir del código objeto o binario. Aunque es posible lograrlo en gran medida, existen limitaciones importantes que debemos asumir. Al realizar ingeniería inversa, no es posible recuperar los comentarios que el programador original escribió, ni tampoco los nombres de las variables que utilizó. Además, es muy probable que no se pueda determinar con total exactitud el tipo de dato original o el tamaño exacto que el desarrollador definió, ya que mucha de esa información se pierde durante la compilación.

A pesar de estas limitaciones, el objetivo es obtener una estructura de código que replique con exactitud el comportamiento del programa fuente. Para lograrlo, es necesario conocer profundamente cómo el compilador maneja las estructuras y cómo las traduce según la **arquitectura objeto** (como x86 de 32 o 64 bits, ARM o MIPS) y las **optimizaciones** aplicadas. Dependiendo de si el compilador optimizó el código para ganar velocidad o ahorrar espacio, el resultado final en lenguaje máquina puede variar drásticamente, lo que obliga al analista a identificar estos patrones para "deshacer" el camino y volver a un lenguaje comprensible.

Una vez que se han traducido estas estructuras básicas, el analista puede avanzar en la ingeniería inversa dando nombres significativos a las variables, funciones y estructuras detectadas, basándose en su comportamiento. En este aprendizaje, se utilizarán ejemplos en lenguajes **C y C++** analizando su equivalente en código objeto (principalmente ensamblador x86 de 32 bits, aunque también se verán casos en 64 bits y ARM mediante compiladores cruzados). El estudio abarcará desde los tipos de datos más básicos y variables simples hasta los complejos objetos del paradigma de programación orientada a objetos en C++, utilizando herramientas estándar como el compilador GCC y el depurador GDB en plataformas Linux.

## Implementación y Análisis de Variables en Memoria

La variable es la estructura de datos más simple en C, pero su implementación física depende directamente del tipo de dato declarado y de la arquitectura (32 o 64 bits). El **tamaño en bits** determina el rango de valores que puede almacenar; por ejemplo, en una arquitectura de 32 bits, un `char` ocupa 8 bits (1 byte), un `short` 16 bits (word) y un `int` o `long` 32 bits (dword). Es crucial entender que en arquitecturas de 64 bits existen diferentes modelos de implementación (como LP64 o LLP64), donde el tamaño de un `long` o de un `pointer` (puntero) puede variar entre 32 y 64 bits según el compilador. Estos detalles son vitales en auditorías de seguridad, ya que una mala interpretación del tamaño de un entero al compilar en arquitecturas distintas es una de las causas más comunes de vulnerabilidades por **desbordamiento de búfer** (buffer overflow).

A nivel de organización interna, las variables se comportan de forma distinta según su ámbito. Las **variables locales** se almacenan en la **pila (stack)** y el procesador utiliza registros específicos como base para localizarlas (el registro `ESP` en x86 o `RBP` en x64). Por el contrario, las **variables globales** se sitúan fuera de las funciones y se almacenan en secciones de datos fijas: la sección `.data` para variables ya inicializadas y la sección `.bss` para las que no tienen un valor inicial. Al usar un depurador como GDB, podemos inspeccionar directamente estas direcciones de memoria, aunque el orden de los datos puede parecer confuso debido al formato **Little-endian**, que almacena los bytes de menor peso en las direcciones más bajas.

Al realizar ingeniería inversa, la dificultad radica en que, sin símbolos de depuración, no conocemos el nombre ni el tipo original de la variable. Solo podemos deducir su naturaleza observando las **directivas de tamaño** que utiliza el código objeto para manipularlas. Por ejemplo, en x86/64, el uso de `BYTE PTR` nos indica un `char`, `WORD PTR` un `short`, `DWORD PTR` un `int` y `QWORD PTR` un tipo de 64 bits como `long long`. Además, el compilador suele aplicar una **alineación de memoria** por optimización; esto significa que puede reservar más espacio del estrictamente necesario (rellenando con ceros o dejando huecos) para que el procesador acceda a las direcciones de forma más rápida, lo que puede despistar al analista al calcular el tamaño real de una estructura.

Finalmente, el comportamiento varía notablemente en otras arquitecturas como **ARM**. A diferencia de x86, ARM suele necesitar dos instrucciones para realizar una asignación: una para cargar el valor literal en un registro y otra para almacenarlo en la dirección de memoria correspondiente (usando instrucciones como `strb` para bytes o `strh` para words). En ARM, para inicializar una variable de 64 bits (`qword`), se requieren incluso dos registros (como `r3` y `r4`) para cubrir el espacio total. Para confirmar estos detalles con exactitud, es muy útil compilar el código fuente directamente a ensamblador (usando comandos como `gcc -S`) y examinar las directivas `.size`, que revelan el número exacto de bytes que el compilador ha reservado para cada objeto global.

### Alcance y Visibilidad de las Variables

El alcance define la "zona de vida" de una variable dentro del código fuente. Aunque en C existen matices, podemos resumirlos en cuatro escenarios principales que el analista debe saber identificar:

- **Variables Globales:** Se declaran fuera de cualquier función. Son accesibles desde cualquier punto del programa y su dirección de memoria es fija durante toda la ejecución.
    
- **Variables Locales:** Se declaran dentro de una función. Solo son accesibles mientras esa función se está ejecutando y, por lo general, viven en la **pila (stack)**.
    
- **Parámetros de Función:** Se comportan como variables locales, pero su valor inicial es otorgado por quien llama a la función.
    
- **Variables de Bloque:** Introducidas en el estándar C99, son variables locales limitadas a un bloque específico (como el interior de un bucle `for`). En el binario, estas variables se suelen tratar como locales de la función, pero su "validez" lógica es restringida.
    

---

### Modificadores de Almacenamiento: Static y Register

Para un ingeniero inverso, los modificadores `static` y `register` cambian drásticamente dónde debemos buscar el dato:

- **El modificador `static`:** Cuando una variable local se marca como estática, deja de almacenarse en la pila y se mueve a la sección de datos del binario (`.data` si está inicializada o `.bss` si no lo está). Esto permite que la variable conserve su valor entre diferentes llamadas a la misma función. Al analizar el binario, veremos que la función accede a una dirección de memoria fija (fuera de la pila) para leer o actualizar este valor.
    
- **El modificador `register`:** Es una sugerencia al compilador para que, en lugar de usar la memoria RAM (pila), mantenga la variable directamente en un **registro del procesador** (como `EBX` en x86). Esto se hace por velocidad. Si hay registros disponibles, el compilador los asignará, y en el binario no veremos accesos a memoria para esa variable, sino operaciones directas entre registros.
    

---

### Análisis en Arquitecturas (x86 y ARM)

Al observar el código objeto, estas diferencias se manifiestan de formas muy específicas que permiten reconstruir la intención original del programador:

- **En x86 (32/64 bits):**
    
    - Una variable local estándar se identifica por accesos relativos al registro de la pila, como `DWORD PTR [esp+0x18]`.
        
    - Una variable `register` se delata cuando vemos, por ejemplo, que un valor se mueve directamente a `ebx` y se opera con él sin pasar por la pila.
        
    - Las variables de bucle (como la `i` de un `for`) aparecen en el binario como una dirección de la pila (ej. `[esp+0x1c]`). Aunque para el compilador es visible en toda la función, para el programador solo existe dentro del bucle.
        
- **En ARM (32 bits):**
    
    - La lógica es similar pero la sintaxis cambia. Las variables locales usan el registro `R11` (Frame Pointer) como base, por ejemplo: `str r3, [r11, #-20]`.
        
    - Para las variables `static`, ARM utiliza un método curioso: almacena la dirección de memoria de la variable cerca del código (usando el contador de programa `PC` como referencia) y luego accede a ella. Esto se observa en instrucciones que cargan una dirección desde una posición relativa al `PC`.
### Los Arrays (Vectores y Matrices)

Un **array** es una variable que almacena múltiples elementos del mismo tipo de forma **consecutiva en la memoria**. Esta característica es la que permite al ingeniero inverso identificarlos: si ves una serie de instrucciones que acceden a posiciones de memoria pegadas unas a otras (por ejemplo, saltando de 4 en 4 bytes para un array de enteros), probablemente estés ante un array.

- **Dimensiones:** Pueden ser unidimensionales (vectores), bidimensionales (matrices, que simulan una tabla con filas y columnas) o tener incluso más dimensiones.
    
- **Cadenas de caracteres:** En C, las cadenas son simplemente arrays de tipo `char`. Se pueden inicializar letra a letra o entre comillas dobles. En este último caso, el compilador añade automáticamente un **carácter nulo (`\0`)** al final para marcar dónde termina el texto, un detalle vital para no leer basura de la memoria.
    

---

### Análisis de Arrays en x86 y ARM

Cuando analizamos el código objeto de un array, la clave está en cómo se inicializan y se accede a sus elementos:

- **En x86 (32/64 bits):** Se observa cómo el valor de cada elemento se mueve directamente a una dirección de memoria calculada. Por ejemplo, si accedes a `vector[1][2]`, verás una instrucción `MOV` que apunta exactamente a la dirección de memoria resultante de sumar los índices al inicio del array.
    
- **Cadenas y Secciones:** Cuando una cadena se declara como un puntero (`char *p = "hola"`), el compilador guarda el texto en la sección **`.rodata`** (datos de solo lectura). Esto optimiza el programa, ya que el valor se crea en tiempo de compilación y no se tiene que "construir" en tiempo de ejecución, ahorrando pasos al procesador.
    
- **En ARM:** El comportamiento es similar, pero utiliza una técnica de "pool de datos". Verás que el programa hace referencia a direcciones al final de la función para cargar los valores desde la sección `.rodata` hacia los registros y luego hacia la pila.
    

---

### Punteros: Las "Direcciones" de la Memoria

El **puntero** es uno de los tipos de datos más potentes y especiales de C. No guarda un valor común (como un 5 o una 'A'), sino que guarda una **dirección de memoria** que apunta a otra variable.

- **Tamaño:** El puntero en sí siempre ocupa lo mismo según la arquitectura: **32 bits (4 bytes)** en sistemas de 32 bits y **64 bits (8 bytes)** en sistemas de 64 bits.
    
- **Identificación:** En ingeniería inversa, identificamos un puntero cuando vemos una instrucción que carga un valor y luego utiliza ese mismo valor como una dirección para otra operación (lo que se conoce como **indirección**). El compilador sabe cuánto ocupa el valor al que apunta el puntero, lo que le permite calcular correctamente los saltos de memoria.
    

---

### Estructuras (Structs)

Las **estructuras** son similares a los arrays en el sentido de que agrupan datos, pero con una diferencia fundamental: cada uno de sus elementos (miembros) puede ser de un **tipo diferente** (un entero, un carácter y un puntero juntos, por ejemplo).

- **Realidad en el binario:** Para el programador, una estructura es un objeto unido. Sin embargo, **para el compilador y para el binario, la estructura no existe como tal**. El compilador trata cada miembro de la estructura como si fuera una variable independiente.
    
- **Acceso a miembros:** En el código desensamblado, verás accesos a la memoria con diferentes desplazamientos (offsets) desde una dirección base. Si una estructura empieza en la dirección `X`, el primer miembro estará en `X`, el segundo en `X+4`, etc. Reconstruir la estructura original requiere que el analista identifique que todos esos accesos pertenecen a un mismo "paquete" de datos relacionados.

### El Desafío de Reconstruir Estructuras

A nivel de código objeto, identificar una estructura puede ser una tarea casi imposible si esta solo se usa de forma local en una función. Esto se debe a que el compilador descompone la estructura y accede a sus miembros como si fueran variables locales independientes, sin dejar rastro de que están relacionadas. En estos casos, el analista solo puede sospechar su existencia basándose en el **contexto del programa** (como mensajes de error, protocolos conocidos o el flujo lógico de los datos), pero el lenguaje ensamblador por sí solo no ofrece una conexión explícita.

Sin embargo, existe un escenario muy común que facilita enormemente esta labor: el **paso por referencia**. Cuando una estructura se pasa como argumento a una función (usando un puntero), el comportamiento en el código objeto cambia:

- **Identificación por Base y Desplazamiento:** El compilador almacena la dirección base de la estructura en un registro (por ejemplo, `EBX` en x86 o `R4` en ARM).
    
- **Accesos Contiguos:** Para acceder a los diferentes miembros, se utiliza esa base junto con un desplazamiento o _offset_ (por ejemplo, `STR valor, [base, #8]`).
    
- **Deducción Estructural:** Al ver múltiples accesos que dependen de una misma base registrada, el analista puede identificar que se trata de una estructura y reconstruir sus campos midiendo la distancia entre esos desplazamientos.
    

---

### Uniones: Compartiendo el mismo espacio

Las **uniones** (`union`) son tipos de datos cuya sintaxis es casi idéntica a las estructuras, pero su funcionamiento interno es radicalmente distinto. Mientras que en una estructura cada elemento tiene su propio espacio de forma consecutiva, en una unión **todos los miembros comparten la misma dirección de memoria**.

Esto implica varias particularidades para la ingeniería inversa:

- **Superposición de Datos:** Al asignar un valor a un miembro de la unión, se sobrescriben automáticamente los demás. Por ejemplo, si una unión tiene un campo de 4 bytes (`long`) y otro de 2 bytes (`short`), al escribir en el segundo se modificará la mitad del primero. Esto se observa claramente en los volcados hexadecimales, donde valores como `0xDEAD` pueden aparecer sobreescritos por otros datos de la misma dirección.
    
- **Misma Dirección en el Binario:** En el código objeto (como se ve en arquitecturas x86), todos los accesos se realizan a la **misma dirección de pila** (por ejemplo, `[ESP+0x1C]`), sin importar si el dato que se está moviendo es un carácter, un entero o un puntero.
    
- **Identificación por Directiva:** La única forma de saber qué miembro se está usando en cada momento es observar la directiva de tamaño de la instrucción (`BYTE PTR`, `WORD PTR`, `DWORD PTR`), ya que todas apuntarán al mismo sitio pero manejarán distintas cantidades de información.
    

---

### Comparativa en Arquitecturas

Tanto en x86 como en ARM, la lógica se mantiene pero con herramientas propias de cada procesador. En x86 se suele utilizar el registro de pila `ESP` como referencia constante para estos accesos superpuestos. En ARM, es común ver cómo se utiliza el **Puntero de Pila (SP)** o registros de propósito general cargados con direcciones de la sección de datos para manipular estos elementos que comparten ubicación. Comprender esta "superposición" es la clave para no confundir una unión con un simple error de lógica o una variable que cambia de uso constantemente.

### La Naturaleza de los Objetos en el Binario

En C++, los objetos son esencialmente estructuras evolucionadas. Para el compilador, los atributos de un objeto se procesan de la misma forma que los elementos de una estructura: se colocan de forma contigua en memoria. Sin embargo, la gran diferencia radica en las funciones:

- **Funciones no virtuales:** No se guardan dentro del objeto. El objeto solo contiene la dirección de inicio de la función. Se invocan mediante un desplazamiento (_offset_) fijo.
    
- **Funciones virtuales:** Estas son más complejas. Se invocan a través de un puntero especial que apunta a una **tabla virtual (vtable)** interna del objeto. Esta tabla es la que permite el polimorfismo en tiempo de ejecución.
    
- **Visibilidad (Público/Privado):** Es importante notar que las etiquetas `public`, `private` o `friend` **desaparecen por completo** en el código objeto. Son meras restricciones para el programador en el código fuente; una vez compilado, cualquier parte del código con la dirección de memoria adecuada puede acceder a esos datos.
    

---

### La Estrategia del Puntero "this"

La clave maestra para identificar un objeto en ingeniería inversa es el puntero **`this`**. Cuando un método de una clase accede a sus atributos, necesita saber sobre qué instancia específica está trabajando.

- **Paso implícito:** A diferencia de una estructura normal donde tú pasas el puntero manualmente como argumento, en C++ el compilador pasa el puntero `this` de manera **implícita**.
    
- **Identificación en registros:** En el código objeto, verás que antes de llamar a una función de clase, se carga una dirección de memoria en un registro (comúnmente `ECX` en x86 usando la convención _thiscall_, o a través de la pila/otros registros según la arquitectura). Si ves una función que parece no recibir argumentos en el código fuente, pero en el binario recibe un puntero base que luego se usa para acceder a variables contiguas, estás ante un **método de un objeto**.
    

---

### Identificación mediante el Constructor y "new"

Si el análisis de los métodos no es suficiente, existe una señal inequívoca: la **inicialización**.

1. **El Operador `new`:** Cuando se utiliza `new`, el código objeto muestra primero una llamada a una función de reserva de memoria (como `malloc` o un operador `new` sobrecargado).
    
2. **El Constructor:** Inmediatamente después de reservar la memoria, se invoca al constructor. El constructor es una función especial que tiene el mismo nombre que la clase y no devuelve ningún tipo.
    
3. **La firma del Constructor:** En el binario, el constructor recibirá el puntero de la memoria recién reservada como su puntero `this` para inicializar los atributos. Ver una reserva de memoria seguida de una llamada a función que opera sobre esa misma dirección es la prueba definitiva de la creación de un objeto.
    

---

### Ambigüedad entre Objetos y Estructuras

Es vital que el analista comprenda que, en muchos casos, el código objeto generado para un objeto con tres enteros es **idéntico** al de una estructura con tres enteros o incluso al de tres variables locales independientes declaradas una tras otra. La abstracción de "objeto" es para el programador; para el procesador, solo son bytes en la pila o el montón (_heap_). La distinción solo se vuelve clara cuando empezamos a ver la relación entre las funciones (métodos) y cómo estas comparten ese puntero base común para manipular los datos.

### La vtable como Identificador de Objetos

El método definitivo para confirmar que estamos ante un objeto (y no una simple estructura) es la identificación de la **vtable**. Las vtables son tablas de punteros a funciones que el compilador crea automáticamente para las clases que tienen métodos virtuales. En el binario, cada objeto de esa clase contiene un atributo implícito: un **puntero a la vtable**.

- **Implementación en Memoria:** Como se observa en los diagramas, este puntero se coloca generalmente al inicio o al final de los atributos del objeto. Al analizar el código, si vemos un puntero que no fue declarado por el programador pero que el compilador utiliza para buscar direcciones de funciones, estamos ante la referencia a la vtable.
    
- **Utilidad en Ingeniería Inversa:** Identificar la vtable permite reconstruir el comportamiento de una clase incluso si ha habido herencia. Cuando una clase hija sobrecarga un método de la clase base, la vtable apuntará a la nueva implementación.

### Análisis del Flujo de Control (CFG) y Llamadas Dinámicas

La presencia de métodos virtuales supone un reto para el análisis estático (revisar el código sin ejecutarlo), ya que las llamadas no se hacen a una dirección fija, sino a través de un registro. Esto complica la creación de un **Grafo de Control de Flujo (CFG)** preciso.

1. **Cálculo de la Dirección:** Para invocar un método virtual, el compilador parte del puntero `this`, accede al puntero de la vtable y luego aplica un **desplazamiento (offset)** para llegar a la función específica.
    
2. **Identificación de Métodos:** En arquitecturas de 64 bits, los desplazamientos suelen ir de 8 en 8 bytes. Por ejemplo:
    
    - Un desplazamiento **0** indica el primer método virtual de la tabla (ej. `foo_public()`).
        
    - Un desplazamiento **8** indica el segundo método contiguo (ej. `foo_public2()`).
        
3. **Uso de Registros:** Es común ver instrucciones como `CALL rax` o `CALL reg`. Para saber qué función se está llamando realmente, el analista debe "rastrear" hacia atrás en el código cómo se ha calculado el valor de ese registro (`rax`) basándose en la base de la vtable y el índice del método.

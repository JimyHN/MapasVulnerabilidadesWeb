
Un compilador es un programa qeu lee un programa escrito en un lenguaje, el lenguaje fuente, y lo traduce a un programa equivalente en otro lenguaje, el lemguaje obketo.

Como parte importante de este proceso de traducción, el compilador informa a su usuario de la presencia de errores en el programa fuente.

Los compiladores permiten escribir código fuente en lenguajes de alto nivel -es decir, en lenguajes no dependientes de la arquitectura del ordenador en el que se ejecute-, así como que el lenguaje sea fácilmente interpretable por un ser humano. Está lejos de ser una lista de comandos secuenciales, como venía siendo el lenguaje ensamblador u otros lenguajes de bajo nivel.

Lenguajes de bajo nivel son estos masocas de **ensamblador, power shell, etc** y de alto nivel son **Java, JavaScript, C#, C++, .NET, Python...**

Los lenguajes de alto nivel han permitido un desarrollo exponencial de softwares que se adaptan a las necesidades de los usuarios y funcionan sin prácticamente cambios en diferentes arquitecturas y tipos de ordenadores.

# 2.5 Análisis léxico

### 2.5.1 De Lexemas a Expresiones Regulares

Para que un ordenador reconozca un componente léxico, no basta con darle una descripción vaga; necesitamos una **especificación matemática**. Aquí es donde entran las **Expresiones Regulares (Regex)**.

Una **Regex** es un patrón que describe un conjunto de cadenas. Por ejemplo, para reconocer un número entero, no escribimos todos los números posibles, sino un patrón como `[0-9]+` (que significa "uno o más dígitos"). 

Es fundamental entender la jerarquía:

- **Alfabeto:** Los ladrillos (letras, números).
- **Lexema:** La palabra real en el código (ej: `3.14`).
- **Patrón (Regex):** La regla que dice cómo debe ser esa palabra.
- **Token:** El nombre que le damos a ese grupo (ej: `NUM_FLOTANTE`).

### Ejemplo: `[0-9]{4}[BCDFGHJKLMNPQRSTVWXYZ]{3}`

Este "molde" funciona así:

- **`[0-9]{4}`**: Le dice al ordenador: "Busca exactamente **4 números** seguidos". El `[0-9]` define que solo valen dígitos y el `{4}` dice cuántos.
- **`[BCDFGHJKLMNPQRSTVWXYZ]{3}`**: Le dice: "Después de los números, busca exactamente **3 letras**". Fíjate que en el molde solo hemos puesto las letras permitidas (en las matrículas no se usan vocales para evitar palabras malsonantes o confusiones).

Si el analizador lee un texto, esto es lo que pasa:

1. **`1234ABC`**: No encaja. Tiene una "A" (vocal), y nuestro molde dice que las vocales no pasan. **Error.**
2. **`123BCD`**: No encaja. Solo tiene 3 números y el molde exige 4. **Error.**
3. **`5566KRT`**: **¡MATCH!** Encaja perfectamente en el molde. El analizador lo guarda y le pone la etiqueta de "Matrícula válida".

<u><b>Eso son las expresiones Regex</u></b>

### 2.5.4. LEX y FLEX: Automatización del análisis

Escribir esos `switch-case` a mano es tedioso y propenso a errores. Por eso existen herramientas como **LEX** o su versión moderna y libre, **FLEX (Fast Lexical Analyser)**.

FLEX es un **generador de analizadores léxicos**. Su funcionamiento es fascinante:

1. Tú le das un archivo de configuración (`.l`) con las expresiones regulares y la acción en C que quieres que haga (ej: "si ves un número, devuélvelo como token ENTERO").
2. FLEX lee eso y **genera automáticamente un código en C** (`lex.yy.c`) que contiene todo el sistema de estados y movimientos que vimos antes.
3. Ese código generado se compila y listo: ya tienes un analizador léxico ultra eficiente sin haber escrito ni un solo `if` manualmente.

### 2.6. El Analizador Sintáctico (Parser)

Su misión es recibir la lista de tokens del paso anterior y verificar que la estructura del programa sea correcta. Piensa en esto como la gramática de un idioma: puedes tener las palabras "perro", "el" y "corre", pero solo "el perro corre" es sintácticamente correcto.

Este análisis permite:

- **Construir un Árbol:** Genera una representación jerárquica llamada **Árbol de Análisis Sintáctico**.
    
- **Detectar errores:** Si pones un `if` sin cerrar el paréntesis, aquí es donde salta el error de "syntax error".
    
- **Facilitar la traducción:** Al dar una estructura lógica al código, es mucho más fácil pasarlo después a código máquina.
    

---

### 2.6.1. Gramáticas Independientes del Contexto (GIC)

Para definir las reglas de un lenguaje de programación, las Expresiones Regulares no son suficientes (porque no pueden manejar estructuras recursivas o anidadas, como paréntesis dentro de paréntesis). Por eso se usan las **GIC**, que suelen escribirse en una notación llamada **BNF** (Backus-Naur Form).

Una gramática se compone de cuatro elementos fundamentales:

1. **Terminales:** Son los símbolos básicos que aparecen en el código (ej: las palabras clave `if`, `else`, los números o los operadores `+`, `-`).
    
2. **No Terminales:** Son variables sintácticas que representan estructuras (ej: `prop` para una proposición, `expr` para una expresión matemática). No aparecen en el código final, son solo para organizar las reglas.
    
3. **Símbolo Inicial:** Es el "título" de la gramática, el punto por el que empieza a analizarse todo el programa.
    
4. **Producciones:** Son las reglas que dicen cómo se pueden combinar los símbolos. Se escriben como una flecha: `V → w` (el grupo `V` se puede sustituir por el contenido `w`).
    

---

### Estrategias de Análisis: Descendentes vs. Ascendentes

Existen dos formas de construir el árbol de análisis mientras se lee el código (siempre de izquierda a derecha):

- **Analizadores Descendentes (Top-Down):** Empiezan por la "raíz" (el símbolo inicial) y van intentando predecir qué reglas encajan para llegar a las "hojas" (el código real). Es como intentar adivinar el final de una frase desde que empieza.
    
- **Analizadores Ascendentes (Bottom-Up):** Empiezan por las palabras reales del código (las hojas) y van agrupándolas en estructuras más grandes hasta llegar a la raíz. Es como montar un puzzle desde las piezas sueltas hacia arriba.
    

---

### 2.6.2. Derivaciones y Árboles

Una **derivación** es la secuencia de pasos que seguimos para demostrar que una cadena pertenece a una gramática. Hay dos estilos:

- **Derivación por la izquierda:** En cada paso, siempre sustituimos primero el símbolo "No Terminal" que esté más a la izquierda.
    
- **Derivación por la derecha:** Sustituimos siempre el que esté más a la derecha.
    

**El problema de la Ambigüedad:** En tus capturas se muestra un ejemplo crucial: la cadena `1 + 1 + 1`. Dependiendo de si la gramática está bien diseñada, se podrían generar **dos árboles distintos** para la misma frase. Si esto pasa, se dice que la gramática es **ambigua**. Esto es un problema grave porque el compilador no sabría qué operación hacer primero, lo cual podría cambiar el resultado del programa.

### 2.7. Analizadores sintácticos LR

Los analizadores **LR** son herramientas de tipo **ascendente** (Bottom-Up). Su nombre tiene truco: la **L** significa que lee la entrada de izquierda a derecha (_Left-to-right_) y la **R** que construye la derivación más a la derecha (_Rightmost derivation_) pero al revés, desde las hojas hasta la raíz.

Un analizador LR es como un operario con una **pila** (donde guarda lo que va leyendo) y una **tabla de instrucciones** que le dice qué hacer en cada momento.

#### Los componentes principales:

- **Programa conductor:** El motor que ejecuta el algoritmo.
    
- **Tabla de análisis:** El "cerebro". Tiene dos partes: **Acción** (qué hacer con los terminales como `+` o `id`) y **Goto** (a qué estado saltar cuando terminamos de reconocer una estructura mayor).
    

---

### El Algoritmo de Reconocimiento (Shift-Reduce)

Este es el proceso lógico que sigue el analizador para entender tu código, paso a paso:

1. **Búsqueda:** Mira el primer carácter que tiene delante y el estado en el que se encuentra su memoria (la pila) para consultar la tabla de **Acción**.
    
2. **Desplazamiento (Shift):** Si la tabla dice _shift_, el analizador "se traga" el carácter, lo mete en la pila junto con un número de estado nuevo y pasa al siguiente símbolo. Es como ir guardando piezas de un puzzle.
    
3. **Reducción (Reduce):** Este es el momento clave. Si la tabla dice _reduce_, significa que lo que hay en el tope de la pila ya forma una regla completa (por ejemplo, ha encontrado un número, un `+` y otro número). Entonces saca esas piezas y las sustituye por una sola etiqueta (como `EXPRESIÓN`).
    
    - Después mira la tabla **Goto** para saber en qué estado debe quedarse tras esta simplificación.
        

---

### 2.7.1. Analizadores LALR

En la práctica, los analizadores LR puros pueden generar tablas gigantescas y lentas. Por eso se usan los **LALR** (_Lookahead-LR_). Son una versión optimizada que combina estados similares para que la tabla sea mucho más pequeña y manejable sin perder apenas potencia. La mayoría de herramientas que generan compiladores automáticamente (como Yacc o Bison) utilizan este método.

---

### 2.8. Análisis Semántico

Una vez que sabemos que la frase está bien escrita (sintaxis), el **Análisis Semántico** comprueba que tenga **sentido lógico**. Por ejemplo: la frase "El coche se come un helado" es correcta gramaticalmente (Sujeto + Verbo + Objeto), pero semánticamente es un error. En programación, esto ocurre cuando intentas sumar un texto con un número o usas una variable que no has declarado.

Este proceso se llama **Traducción dirigida por la sintaxis**. Básicamente, a cada regla de la gramática le "pegamos" una acción o atributo.

#### Herramientas del análisis semántico:

- **Atributos:** Información extra que guardamos de cada símbolo (como el tipo de dato: int, float, string).
    
- **Definiciones dirigidas por la sintaxis:** Reglas de alto nivel que dicen cómo calcular esos atributos mientras se recorre el árbol.
    
- **Esquemas de traducción:** Indican el orden exacto en el que se deben ejecutar las acciones (emitir código, guardar en la tabla de símbolos o lanzar un mensaje de error).
    

Al final de esta fase, el compilador ya no solo tiene un "dibujo" de tu código, sino que entiende qué quieres hacer y está listo para empezar a generar el código final.

### La Gramática de la Calculadora

Para que la calculadora funcione, primero definimos sus reglas de juego mediante una gramática. En la imagen ves tres niveles:

- **E (Expresión):** Maneja las sumas.
    
- **T (Término):** Maneja las multiplicaciones.
    
- **F (Factor):** Maneja los números (**dígitos**) y los paréntesis.
    

Esta estructura jerárquica no es casualidad; está diseñada así para que el compilador respete la **jerarquía de las operaciones**. Al poner la multiplicación en un nivel "más profundo" que la suma, la calculadora siempre resolverá primero los productos antes de sumar los resultados.

---

### Bison: El cerebro de la calculadora

**Bison** es un generador de analizadores sintácticos. Como ves en el código, tú no escribes cómo leer los datos, sino que defines **reglas semánticas** asociadas a la gramática.

- **Símbolos `$$` y `$n$`:** Son la clave del cálculo. `$$` representa el resultado de la regla actual (el lado izquierdo de la flecha), mientras que `$1`, `$2`, `$3`, etc., representan los valores de los componentes del lado derecho.
    
- **Ejemplo:** En la regla `expr : expr '+' termino { $$ = $1 + $3; }`, le estás diciendo a Bison: "Cuando reconozcas una suma, el valor total (`$$`) será la suma del primer valor (`$1`) y el tercero (`$3`)".
    

---

### Flex: El lector de números

Para que Bison pueda sumar, alguien tiene que leer los caracteres del teclado y decirle qué son. De eso se encarga **Flex** (el analizador léxico). En el archivo `Lex.l` ves una regla sencilla: `digito [0-9]+`. Cuando Flex detecta uno o más números en la entrada, realiza dos acciones:

1. Usa `sscanf` para convertir ese texto en un número real y guardarlo en la variable **`yylval`**.
    
2. Devuelve el token **`DIGITO`** a Bison para avisarle de que acaba de encontrar un número listo para ser usado en una operación.
    

---

### La Integración Final

Finalmente, el programa une ambas piezas. En el código de la calculadora ves la línea `#include "lex.yy.c"`. Esto significa que el código generado automáticamente por Flex se inserta dentro del código de Bison.

Cuando ejecutas el programa, la función **`yyparse()`** toma el control. Esta función llama constantemente al lector de Flex para pedirle piezas, las va apilando y, en cuanto detecta que tiene una operación completa (como una suma), ejecuta el código C que escribiste entre llaves (como `{ $$ = $1 + $3; }`) e imprime el resultado final por pantalla. Es la culminación de todo el proceso: desde unos y ceros hasta una lógica matemática funcional.

### 2.9. Generación de Código Intermedio

El **Código Intermedio** es una representación del programa que no es ni el lenguaje de alto nivel (C++) ni el código máquina final (binario). Es un paso intermedio diseñado para ser:

1. **Fácil de producir** a partir del análisis semántico.
    
2. **Fácil de traducir** a cualquier arquitectura de procesador (Intel, ARM, etc.).
    

La gran ventaja es la **portabilidad**: si quieres que tu compilador funcione para un procesador nuevo, solo tienes que cambiar la "etapa final" (backend), manteniendo intacta toda la lógica anterior.

---

### 2.9.1. Código de Tres Direcciones

Es la forma más común de código intermedio. Se llama así porque cada instrucción tiene, como máximo, **tres direcciones**: dos para los operandos y una para el resultado. La forma general es `x := y op z`.

Como el procesador real no puede resolver operaciones complejas de un tirón, el compilador descompone expresiones largas.

- **Ejemplo:** `x + y * z` se convierte en:
    
    1. `t1 := y * z` (donde `t1` es una variable temporal).
        
    2. `t2 := x + t1`.
        

Esto obliga al programa a ser una secuencia lineal de pasos simples, muy parecida a cómo piensa el hardware.

---

### 2.9.2. Tipos de Proposiciones de Tres Direcciones

Existen varios "moldes" de instrucciones que el compilador utiliza para traducir el código fuente:

- **Asignaciones:** Operaciones binarias (`x := y + z`) o unarias (`x := -y`).
    
- **Copia:** Pasar el valor de una variable a otra (`x := y`).
    
- **Saltos (Gotos):** Pueden ser incondicionales (`goto L`) o condicionales (`if x op y goto L`). Son los que permiten crear bucles y condicionales.
    
- **Procedimientos:** Gestión de funciones mediante parámetros (`param x`) y llamadas (`call p, n`).
    
- **Índices y Punteros:** Operaciones con arrays (`x := y[i]`) o direcciones de memoria (`x := &y`).
    

---

### 2.10. Generación de Código y Optimizaciones

Llegamos a la fase de "limpieza". El objetivo de la **optimización** es que el programa ocupe menos espacio, corra más rápido o ambas cosas. Es importante saber que generar el código "perfecto" es matemáticamente imposible (indecidible), por lo que los compiladores usan trucos llamados **heurísticas** para mejorarlo lo máximo posible.

#### Transformaciones que preservan la función:

Son cambios que el compilador hace con total seguridad de que el resultado final del programa no va a variar. Las principales son:

1. **Eliminación de subexpresiones comunes:** Si el programa calcula lo mismo dos veces sin que cambien los datos entre medias (ej. calcular `4 * i` dos veces), el compilador guarda el resultado la primera vez y lo reutiliza en la segunda, ahorrando tiempo de CPU.
    
2. **Propagación de copias:** Si tenemos `x := y`, el compilador intenta usar directamente `y` en lugar de `x` en las siguientes líneas. Esto a menudo permite borrar la variable `x` por completo más adelante.
    
3. **Eliminación de código inactivo (Dead Code):** El compilador detecta partes del código que nunca se van a ejecutar (como un `if (false) { ... }`) o variables cuyos resultados nunca se usan, y simplemente las borra para que el archivo final sea más ligero.
    
4. **Cálculo previo de constantes (Constant Folding):** Si escribes `x = 2 + 2`, el compilador no le pide al procesador que sume en tiempo de ejecución; directamente pone `x = 4` en el código final.

### Optimizaciones de Lazos (Bucles)

Los bucles son donde los programas pasan la mayor parte del tiempo, por lo que optimizarlos es la forma más rápida de ganar velocidad. Las tres técnicas clave son:

- **Traslado de código:** Si una operación dentro del bucle siempre da el mismo resultado (por ejemplo, `limite - 2`), el compilador la saca del bucle y la hace una sola vez al principio.
    
- **Eliminación de variables de inducción:** El compilador detecta variables que crecen o disminuyen juntas de forma predecible. Esto permite simplificar cálculos complejos.
    
- **Reducción de intensidad:** Es el arte de cambiar "operaciones caras" por "baratas". Por ejemplo, sustituir una multiplicación (que consume muchos ciclos de reloj) por una suma o una resta dentro del bucle.
    

---

### Análisis de Flujo de Datos

Para poder optimizar sin romper nada, el compilador necesita un "mapa" de cómo se mueven los datos.

- **Grafos de Control de Flujo (CFG):** Representan visualmente los caminos que puede tomar el programa (secuencias, `if`, `while`, `case`). Cada "bolita" es un bloque de código y las flechas son los saltos.
    
- **Análisis Global:** El compilador resuelve sistemas de ecuaciones para saber qué valores llegan a cada punto del programa, permitiendo borrar código que nunca se usará o predecir resultados.

### 2.11. Herramientas: GCC vs. LLVM

En la práctica, no construimos compiladores desde cero. Usamos dos gigantes:

1. **GCC (GNU Compiler Collection):** El estándar clásico. Es potente pero más monolítico (como un bloque sólido de herramientas).
    
2. **LLVM:** Es la opción más moderna y modular. Está diseñado como una "caja de piezas" que puedes reutilizar. Es muy popular porque permite crear compiladores para nuevos lenguajes muy rápido y tiene una interactividad excelente (se puede usar incluso desde Python).

### El proceso real en GCC (Ejemplo práctico)

Tus últimas capturas muestran cómo "destripar" el trabajo de GCC usando comandos como `gcc -fdump-passes`. Esto genera archivos que muestran la metamorfosis del código:

1. **Gimple:** Una versión simplificada de C que usa el compilador internamente.
    
2. **SSA (Static Single Assignment):** Una forma donde cada variable se asigna una sola vez. Esto facilita muchísimo las optimizaciones matemáticas.
    
3. **Resultado Optimizado:** La versión final pulida, lista para convertirse en Ensamblador y luego en el binario que ya conocemos.

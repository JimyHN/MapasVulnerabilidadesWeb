Abre Burp Suite y ve a la pestaña Proxy → HTTP History.
Aquí verás todas las peticiones y respuestas que pasan por el proxy.
Busca peticiones donde hayas enviado algún dato como tu nombre, una búsqueda, un comentario.
Haz clic en una de esas peticiones y mira la pestaña Response.
Busca en el HTML de la respuesta si aparece el texto que introdujiste.
🔵 Paso 2/3: Qué hacer
1. Haz clic derecho sobre una petición relevante y selecciona Send to Repeater.
2. En Repeater, localiza el parámetro con tu dato (puede estar en el body como q=miNombre o en la URL).
3. Cambia ese valor por este payload XSS: <b>INYECTADO</b>
4. Pulsa Send y mira la respuesta en el panel de la derecha.
5. Busca en el HTML si tu payload aparece.
🔵 Paso 3/3: Ejemplos de resultado
✔ CORRECTO: El HTML de respuesta contiene el payload escapado:
&lt;b&gt;INYECTADO&lt;/b&gt;
Significa que los caracteres < y > fueron convertidos a entidades HTML. La app es segura.

✘ DEFICIENTE: El HTML de respuesta contiene el payload sin escapar:
<b>INYECTADO</b>
El navegador lo renderizaría como texto en negrita — y si fuera ejecutaría código. Vulnerable a XSS.

🖥️ Paso 1/3: Dónde mirar
Usaremos curl para hacer una petición enviando el payload como parámetro.
curl es como un navegador de línea de comandos — hace peticiones HTTP y muestra la respuesta.
Necesitamos la URL de un endpoint que muestre datos del usuario, por ejemplo un buscador.
🖥️ Paso 2/3: Qué hacer
Ejecuta este comando (sustituye la URL por la real):
curl -s 'https://ejemplo.com/buscar?q=%3Cscript%3Ealert(1)%3C%2Fscript%3E'
El %3Cscript%3E... es el payload XSS codificado en URL ().
Después busca en la salida si aparece el tag script.
🖥️ Paso 3/3: Ejemplos de resultado
✔ CORRECTO: La respuesta muestra el payload escapado:
&lt;script&gt;alert(1)&lt;/script&gt;
Los &lt; y &gt; son la versión escapada de <> — el navegador los mostraría como texto, no los ejecutaría.

✘ DEFICIENTE: La respuesta contiene el tag sin escapar:
<script>alert(1)</script>
Si abres esto en un navegador, ejecutaría el JavaScript. XSS confirmado.

🔵 Paso 1/3: Dónde mirar

En el panel de respuesta, ve a la pestaña Headers y busca la línea que empieza por Set-Cookie:.
🔵 Paso 2/3: Qué hacer
Examina cada atributo de la cookie en la cabecera Set-Cookie:

Busca estos atributos (todos deben estar presentes):
• Secure — solo envía la cookie por HTTPS, nunca por HTTP
• HttpOnly — JavaScript no puede acceder a la cookie (protege contra XSS)
• SameSite=Strict o SameSite=Lax — protege contra CSRF
• Prefijo __Host- o __Secure- en el nombre — garantías adicionales

También comprueba que el Path es / y que no tiene un Domain demasiado amplio.
🔵 Paso 3/3: Ejemplos de resultado

El prefijo __Host- + Secure + HttpOnly + SameSite=Strict es la configuración más segura posible.

✘ DEFICIENTE: Cookie sin atributos de seguridad:
Set-Cookie: session=a3f2e891; Path=/
Sin Secure: la cookie se envía por HTTP. Sin HttpOnly: JavaScript puede robarla. Sin SameSite: vulnerable a CSRF.

V13.4.1Metadatos de versiónVerificar que la aplicación se despliega sin metadatos de control de versiones, incluyendo las carpetas .git o .svn, o de forma que estas carpetas sean inaccesibles tanto externamente como para la propia aplicación.✅ Aplica:
La app se despliega desde un repositorio de código como Git o SVN — lo cual significa que puede existir una carpeta .git accesible si no se configura bien.

❌ No aplica:
El despliegue no involucra repositorios de código fuente — los ficheros se copian manualmente o por otro método.
🔵 Paso 1/3: Dónde mirar
En Burp ve a Proxy → HTTP History.
En el buscador de la parte superior, filtra por /.git o usa la pestaña Target → Site Map.
También puedes usar el scanner de Burp: Dashboard → New Scan y añadir el dominio.
🔵 Paso 2/3: Qué hacer
1. En Repeater, haz peticiones GET manuales a estas rutas comunes:
/.git/HEAD, /.git/config, /.env, /.svn/entries, /web.config
2. Observa el código de respuesta:
404 o 403 = bien protegido
200 con contenido real = expuesto
3. Si /.git/HEAD devuelve 200, el repositorio entero está expuesto — se puede descargar el código fuente.
🔵 Paso 3/3: Ejemplos de resultado
✔ CORRECTO: Las rutas de control de versiones devuelven 404 o 403:
GET /.git/HEAD → 404 Not Found
GET /.env       → 403 Forbidden
✘ DEFICIENTE: El fichero es accesible públicamente:
GET /.git/HEAD → 200 OK
ref: refs/heads/main
Con esto, un atacante puede usar git clone https://ejemplo.com/.git para descargar todo el código fuente.

Comprobaremos si los ficheros de control de versiones y configuración están expuestos públicamente.

for path in /.git/HEAD /.git/config /.env /.svn/entries /web.config /.htaccess; do
  CODE=$(curl -s -o /dev/null -w '%{http_code}' https://ejemplo.com$path)
  echo "$CODE  $path"
done

✔ CORRECTO: Todas las rutas devuelven 404 o 403:
404  /.git/HEAD
403  /.git/config
404  /.env
404  /.svn/entries
✘ DEFICIENTE: Alguna ruta devuelve 200:
200  /.git/HEAD    ← EXPUESTO
200  /.env         ← EXPUESTO (claves API, credenciales BD)
Un .env expuesto puede contener las claves de la base de datos, claves de API de Stripe/AWS, etc.
